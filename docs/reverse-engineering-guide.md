# GPU キャプチャ形式 解析手順書（プラットフォーム共通）

PIX (.wpix) の解析で実際に使った手順を、他のキャプチャ形式（Nsight Graphics、RenderDoc、Xcode GPU Trace、
Android GPU Inspector、Radeon GPU Profiler、ゲーム機向けツール等）にも適用できる形にまとめたもの。
PIX での具体例は [formats/wpix.md](formats/wpix.md)、作業ループの短縮版は [methodology.md](methodology.md)。

---

## 0. 前提と原則

### 0.1 3 つの手掛かりを必ず揃える

| 手掛かり | 何をするか | なぜ必要か |
|---|---|---|
| **既知平文** | 自作アプリに特徴的な値を埋め込み、バイナリ中で探す | 「どこに何があるか」の起点 |
| **差分** | 1 要素だけ変えたキャプチャを複数取り、変化したバイトを見る | フィールド境界・意味の確定 |
| **オラクル** | ツール自身の解釈（テキスト出力、C++ 再生成、API ダンプ）を正解として使う | 推測を検証し、意味を名付ける |

どれか 1 つだけでは推測が残る。3 つ揃うと「推測 → 検証」が機械的に回せる。

### 0.2 自動検証できる形で進める

- デコーダは**ペイロードを過不足なく消費できたか**を必ず判定し、失敗を隠さない。
  1 バイトでも余る・足りない規則はどこかが間違っている。
- 判明した事実には確度を付ける: ✅ 確定（複数キャプチャ + オラクルで検証）/ 🔶 推定 / ❓ 未解明。
- 判明した規則はコードとテストに即反映する（ドキュメントだけに残さない）。

### 0.3 法的・倫理的な確認

- 対象ツールの EULA / 利用規約でリバースエンジニアリングや相互運用目的の解析が許されているか確認する。
- 解析対象は**自分で作ったアプリのキャプチャ**から始める。第三者のアプリのキャプチャを扱う場合、その権利関係を確認する。
- キャプチャにはマシン名・ユーザー名・パス・時刻・リソース内容が含まれることが多い。共有・公開する前に確認する。
- ツールの DLL の逆アセンブルはヒント集め（import、文字列）までに留め、最後の手段とする。

## 1. 準備フェーズ

### 1.1 環境の棚卸し

- キャプチャツール本体とバージョン、**CLI の有無**（自動化の可否が作業量を大きく左右する）
- GPU / OS / ドライバの条件（例: Nsight Graphics は NVIDIA GPU が前提）
- ツールに付属する**オラクルになり得る機能**を列挙する:
  - API 呼び出しのテキスト/CSV 出力（PIX: `pixtool save-event-list`）
  - キャプチャからのコード生成（PIX: `export-to-cpp`、Nsight: C++ Capture）
  - リソース/シェーダの単体書き出し機能
  - 公開されている SDK・ヘッダ・ドキュメント・オープンソースのリーダー

> 形式がオープンソースで実装されているもの（例: RenderDoc の .rdc、gfxreconstruct の .gfxr）は、
> リバースエンジニアリングせずにソースを読むのが最短。本手順は形式が非公開の場合のためのもの。

### 1.2 テストアプリ（キャプチャ対象）を作る

`samples/DX12CaptureTarget` を手本に、対象 API（D3D12 / Vulkan / Metal / GLES …）で作る。要件:

1. **既知の値を埋め込む**（検索しやすいもの）
   - 32bit マジック: `0xDEADBEEF`, `0xCAFEBABE`, `0x13579BDF`（小さい値は誤検出が多いので避ける）
   - float: `1.2345f`, `6.789f`（`0.0`, `1.0` は避ける）
   - 文字列: 固有接頭辞 `GCA_` 付きのオブジェクト名・デバッグマーカー
   - 意味が分かるテクスチャパターン（例: texel = `0xA5000000 | y<<4 | x`）
2. **variant 引数**で全ての既知値が決定的に変わるようにする（差分解析用）。値の種類ごとに変え方を変える
   （+v、`| v`、数を増やす等）と、どのフィールドが動いたか判別しやすい。
3. **manifest 出力**: 埋め込んだ値を JSON に書き出す（テストの正解データになる）。
4. **キャプチャ自動化**: ツールのプログラマティックキャプチャ API（PIX: `WinPixGpuCapturer.dll` の
   `CaptureNextFrame`）や CLI を使い、N フレーム目を取ってファイルに保存し、アプリが自動終了する。
5. **カバレッジを段階的に増やせる構成**: 最初は最小（クリア + 1 ドロー + 1 ディスパッチ）、
   API を追加するたびに既知値も追加する。

### 1.3 キャプチャ取得スクリプト

`scripts/capture_pix.py` と同様に、variant ごとに「キャプチャ + manifest + オラクル出力」を一括生成する。
以後の全作業はこのスクリプトの出力だけを入力にする（手作業のキャプチャを混ぜない）。

## 2. コンテナ層の解析

ゴール: ファイルを「意味のあるデータ塊の列」に分解し、圧縮を解く。

1. **全体を眺める**: `python -m gcap probe FILE --manifest vN.json`
   - 先頭/末尾のマジック、頻出タグ（4〜8 文字の大文字列）、ブロックごとのエントロピー
   - 既知値がそのまま見つかる → 非圧縮。見つからない → 圧縮/暗号化
2. **タグ周辺の構造を読む**: タグ直後の整数がサイズかオフセットかを、次のタグ位置との差で判定する。
   - よくある形: `tag + size + payload`、末尾にディレクトリ（目次）、ヘッダとトレーラの対称構造
   - ディレクトリが末尾にある形式は**後ろから読む**（PIX は DIR テーブルを逆方向に辿る）
3. **圧縮形式の特定**
   - 断片化した文字列（`icrosoft (R) HLSL Shader Compil@` のような）→ LZ 系
   - ツールの DLL の **import テーブル**と文字列を見る（PIX は `cabinet.dll` → Windows Compression API）。
     他には zlib、zstd、lz4、oodle、snappy の名前・マジックを探す
   - 候補を総当たりする（`gcap.probe.try_decompress`）。展開後のサイズがヘッダの値と一致すれば確定
4. **パーサを書き、全ブロックを展開**して、ストリーム/チャンク単位でファイルに書き出す。
   以後はこの展開済みデータを解析する。

チェックリスト:
- [ ] 全バイトがどこかの構造に属している（未説明の隙間がない）
- [ ] 全 variant でパースが通る（ブロック種別の追加漏れがない。PIX では `BLOKDATA` が後から出た）

---

## 3. レコード層の解析

ゴール: 展開データを「1 イベント = 1 レコード」に分割する。

1. 展開データの先頭を見て、繰り返し現れるヘッダ（PIX: `<EVT`）を探す。
2. ヘッダ内の各整数を分類する: 種別 ID / 通し番号 / サイズ / スレッド / タイムスタンプ。
   - サイズは「次のレコード位置 − 現在位置 − ヘッダ長」で検算する
   - 通し番号は**チャンクをまたいで連続しているか**を見る（PIX の seq は全ストリーム共通で、
     ECL などの参照に使われていた）
3. 全レコードを列挙して、種別 ID ごとの件数・サイズ・所属チャンクを一覧にする。

---

## 4. 種別 ID と API の対応付け

ゴール: 種別 ID → API 名（または独自イベント名）の表を作る。

1. オラクル（event list / 生成コード）の**呼び出し順**と、レコードの**通し番号順**を並べて対応を取る。
2. ID の並びに規則がないか調べる:
   - COM/D3D: vtable 順（PIX: 「メソッドを宣言したインターフェースごとの基準値 + その中での順番」）
   - Vulkan: コマンド列挙順 / `vkCmd*` のアルファベット順 / 拡張ごとのブロック
   - Metal: Objective-C セレクタ文字列が埋まっていることが多い
3. 規則が見つかったら、**SDK ヘッダから全メソッド表を自動生成**する（`gcap/d3dmeta/header_parser.py` 方式）。
   Vulkan なら `vk.xml`（registry）、Metal なら SDK の `.h` / `.apinotes` が情報源になる。
4. 残りはツール独自イベント（初期状態、リソースの中身、環境情報、スクリーンショット等）。
   既知値が出てくる位置から構造を逆算する。

## 5. 引数のシリアライズ規則

ゴール: 汎用デコーダで大半の API を読めるようにする。

1. 単純な API（引数が整数だけのもの: Draw / Dispatch / SetStencilRef）から始め、次の基本事項を決める:
   - エンディアン、アラインメント（パディングの有無）、bool のサイズ
   - `this` / ハンドルの表現（ポインタ値のままか、ID に置き換えられているか）
   - 戻り値（HRESULT / VkResult）が記録されているか
2. 次にポインタ・配列・文字列・構造体を含む API で、次を確かめる:
   - null の表現（存在フラグがあるか）
   - 配列の要素数がデータ中に入っているか（入っていれば自己記述的で楽）
   - 構造体内のポインタ（シェーダバイトコード等）の展開方法
   - union（判別フィールドで片方だけか、全メンバか）
   - GPU アドレス / ディスクリプタハンドルの正規化（生アドレスを「リソース + オフセット」に置換していることが多い）
3. 規則を汎用デコーダに実装し、**例外は表にまとめる**（PIX: `UNION_SELECTORS`, `ARRAY_PARAM_OVERRIDES` 等）。
4. 「消費長が一致しないレコード」だけを個別に調べる → 規則を直す、を繰り返す。

コツ:
- 失敗位置（何バイト目で破綻したか）の直前のフィールドが原因であることが多い
- 差分で動いたバイト幅から、フィールドのサイズ（u8/u16/u32/u64）が分かる
- 同じ構造体が複数の API に出るので、1 か所で確定させれば他も読めるようになる

## 6. 状態スナップショットとリソース

ほとんどのキャプチャは「キャプチャ開始時点の状態」を別に持っている。

- リソース生成情報（desc、ヒープ、初期ステート、クリア値）
- リソースの中身（テクスチャのレイアウト: 行ピッチ・サブリソースの並び・プレーン）
- ディスクリプタ / ビュー / サンプラーの中身
- パイプライン（シェーダバイトコード、ルートシグネチャ / パイプラインレイアウト）

検証方法: 既知パターンのテクスチャ・定数バッファ・頂点バッファを書き出して、画像やバイト列で確認する
（PIX ではクリア色 `20 40 60 ff` やテクセル `0xA50000yx` がそのまま見えた）。

---

## 7. 自動検証（テスト）

`tests/test_wpix.py` と同じ 2 段構えにする。

1. **manifest 照合**: デコード結果 == アプリが埋め込んだ値（全 variant）
2. **オラクル照合**: デコード結果 == ツール自身の解釈（オブジェクト ID・順序まで）
3. テストを故意に壊して、失敗することを確認する（テストが本当に効いているかの確認）
4. 大きな節目では、別の担当者（またはサブエージェント）がオラクルと全項目を独立に突き合わせる

---

## 8. 解析結果の活用（自動解析）

デコードができたら、上位の解析を積み上げる。

- コマンドリスト / コマンドバッファの再構成（マーカー階層付き）
- **ドロー / ディスパッチごとの状態解決**（パイプライン、バインドされた実リソース、RT/DS）
- リソースとシェーダの抽出、ルートシグネチャ / パイプラインレイアウトの解析
- 統計（ドロー数、状態変更回数、バリア数、未使用リソース等）、差分（2 つのキャプチャの比較）

## 9. 新しいプラットフォームを追加するときのチェックリスト

```
[ ] 0. EULA・権利関係を確認した
[ ] 1. ツールの CLI / プログラマティックキャプチャ / オラクル機能を調べた
[ ] 2. テストアプリ（既知値・variant・manifest・自動キャプチャ）を作った
[ ] 3. capture_<platform>.py で variant 0..3 + オラクルを一括生成できる
[ ] 4. gcap probe でマジック・エントロピー・既知値ヒットを確認した
[ ] 5. コンテナ / 圧縮を解いた（全バイトの帰属が説明できる）
[ ] 6. レコード層（ヘッダ・通し番号・サイズ）を確定した
[ ] 7. 種別 ID → API 対応の規則を見つけ、ヘッダ/レジストリから表を自動生成した
[ ] 8. シリアライズ規則を汎用デコーダに実装し、消費長チェックで全レコード OK
[ ] 9. 独自イベント（初期状態・リソース・環境情報）をデコードした
[ ] 10. manifest 照合 + オラクル照合のテストが全 variant で通る
[ ] 11. docs/formats/<platform>.md に確度付きで記録した
[ ] 12. tools/gcap/<platform>/ と CLI サブコマンドを追加した
```

### コード配置の規約

```
samples/<API>CaptureTarget/        テストアプリ
scripts/capture_<platform>.py      キャプチャ + オラクル生成
tools/gcap/<platform>/             container.py / events.py / decoder.py / <tool>_events.py / knowledge/
tools/gcap/<api>meta/              SDK ヘッダ・レジストリからのメタデータ生成
tests/test_<platform>.py           manifest + オラクル照合
docs/formats/<platform>.md         形式仕様（確度マーク付き）
```

## 付録: プラットフォーム別メモ（未検証、着手時に確認すること）

| 対象 | 確認すること |
|---|---|
| Nsight Graphics | NVIDIA GPU が必要。C++ Capture 機能がオラクルになるか。[formats/nsight.md](formats/nsight.md) |
| RenderDoc (.rdc) | オープンソースなので形式はソースから分かる。解析よりリーダーの実装が中心 |
| Vulkan 全般 | 種別 ID の規則を `vk.xml` と照合する。pNext チェーンのシリアライズ方法 |
| Xcode GPU Trace (Metal) | `.gputrace` はディレクトリ（バンドル）形式の可能性。plist や SQLite が含まれていないか見る |
| Android GPU Inspector / gfxreconstruct | gfxreconstruct はオープンソース。AGI の独自部分を切り分ける |
| Radeon GPU Profiler (.rgp) | 公開されている仕様・ツールの範囲を先に調べる |
| ゲーム機向けツール | NDA の範囲を必ず確認する。成果物を公開リポジトリに置かない |
